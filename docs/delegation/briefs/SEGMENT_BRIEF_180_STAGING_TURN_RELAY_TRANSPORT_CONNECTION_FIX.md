# Segment Brief 180: Staging TURN Relay Transport Connection Fix

Branch: `wave/stage9-staging-turn-relay-transport-connection-fix`

## Goal

Fix or precisely diagnose the staging TURN relay transport connection blocker without production VPS/env/default changes, LiveKit removal, broad media rewrites, or full manual private/channel smoke.

## Starting State

- Segment 179 is committed locally before this segment.
- Direct staging SFU harness passed.
- Stop/Reset cleanup convergence passed and final active rooms/transports/producers/consumers were `0`.
- TURN harness still failed before consumer creation:
  - create send transport: `pass`
  - create recv transport: `pass`
  - produce local track: `pass`
  - send transport connected: `fail`
  - failure: `mediasoup transport did not connect: new`
- coturn showed redacted relay allocation activity and allocation count returned to zero.
- Production VPS/env/defaults remained untouched.

## Investigation

Code inspection found that the existing TURN harness path already:

- requests backend TURN credentials for both send and receive transport creation when mode is `turn`;
- passes backend-issued TURN credentials into mediasoup-client `iceServers`;
- applies `iceTransportPolicy: "relay"` to the mediasoup-client transport options for both send and receive transports;
- waits for transport connection before the remote-track assertion.

The remaining evidence was insufficient to classify the failure because the browser UI did not report:

- whether the mediasoup-client `connect` event fired;
- whether backend DTLS connect was accepted;
- whether relay-only local ICE candidates were gathered;
- whether a selected candidate pair existed;
- non-secret TURN URL scheme/count/transport-hint metadata;
- non-secret mediasoup server ICE candidate protocol/type metadata.

## Implementation

This segment adds bounded, non-secret diagnostics to the staging smoke path:

- `SfuClientAdapter` now records per-transport diagnostic metadata:
  - connection state;
  - `iceTransportPolicy`;
  - server ICE candidate count/protocol/type;
  - TURN ICE server count;
  - TURN URL scheme count, schemes, and `transport=` hints without host, username, password, or credential values;
  - whether the mediasoup-client `connect` event fired;
  - whether backend transport connect was accepted;
  - selected candidate pair state and candidate types/protocols from `transport.getStats()` where available.
- `SfuSmokeHarness` now displays sanitized transport config diagnostics after send/recv transport creation.
- failed transport waits now include the sanitized connection diagnostics in the failure detail.
- successful transport waits also show sanitized connection diagnostics.

The diagnostics intentionally do not print TURN URLs, TURN usernames, TURN credentials, cookies, auth headers, real IPs, DB URLs, private keys, or secret env values.

## Classification Rules For Rerun

If TURN still fails, classify using the new diagnostics:

- `connectEvent=no`: mediasoup-client did not attempt backend DTLS connect; inspect browser ICE gathering / transport event path.
- `connectEvent=yes connectAccepted=no`: backend transport connect rejected; inspect API logs and DTLS connect response without secrets.
- `connectAccepted=yes localCandidates=none`: browser did not gather usable local candidates; inspect TURN URL/credential/browser policy.
- `connectAccepted=yes localCandidates=relay pairState=none`: relay candidates exist but no candidate pair selected; inspect mediasoup announced address / RTC range / firewall / coturn peer permissions.
- `selectedLocal=relay pairState=succeeded`: relay ICE connected; investigate later DTLS/media path, not initial relay transport connection.
